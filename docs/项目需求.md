# AI 大数据实时风控平台项目需求

## 1. 文档说明

本文档根据项目架构图、当前代码和 `Agents.md` 整理，用于明确项目目标、功能范围和分阶段实现方向。架构图中明确出现的内容作为项目目标；为便于逐步落地而补充的内容会标注为“建议”或“待确认”，不代表已经完成或已经确定。

## 2. 项目目标

构建一个基于 Python 与 AI Agent 的大数据实时风控演示平台。平台接收用户行为事件，经过实时处理、风控规则和 AI 模型分析后生成风险评分，并将结果提供给风控管理平台查看，最后由 AI Agent 辅助分析和解释风险。

项目同时作为学习实践项目。实现过程应让初学者理解各模块的职责、数据流向、接口调用和关键代码，并通过小步迭代提升 Python、数据库、大数据处理、AI 应用和工程协作能力。

## 3. 架构目标与数据流

架构图给出的目标链路如下：

```text
用户行为（登录、下单、支付）
    → Kafka
    → Spark / Flink 实时数据处理
    → 风控规则 + AI 模型
    → 风险评分
    → Redis / MySQL / ClickHouse
    → FastAPI
    → Vue 3 风控管理平台
    → AI Agent
    → 智能风险分析与解释
```

各组件的目标职责：

| 组件 | 目标职责 |
| --- | --- |
| 用户行为事件 | 提供登录、下单、支付等风控分析输入 |
| Kafka | 接收并传递行为事件，缓冲生产端与处理端之间的数据 |
| Spark / Flink | 对事件进行实时处理；具体选型和处理逻辑待确认 |
| 风控规则 | 根据明确的条件识别风险行为 |
| AI 模型 | 为风险判断提供模型分析能力；模型类型和输入特征待确认 |
| 风险评分 | 汇总规则与模型判断，形成可供查询和展示的风险结果 |
| Redis / MySQL / ClickHouse | 分别承担缓存、业务数据存储和分析查询等目标职责；详细分工待确认 |
| FastAPI | 提供后端接口，服务管理平台和 Agent |
| Vue 3 | 提供风控管理平台的前端界面 |
| AI Agent | 根据风险数据辅助分析，并生成便于理解的解释 |

## 4. 功能需求

### 4.1 用户行为事件

- 系统应支持登录、下单、支付三类行为作为项目的示例事件。
- 每类事件需要有可描述的结构化字段，供后续处理、规则判断和模型分析使用。
- 事件字段、唯一标识、时间格式、缺失值处理和重复事件处理方式属于待确认设计项。

### 4.2 实时数据处理

- 系统目标是将行为事件送入 Kafka，并由 Spark 或 Flink 进行实时处理。
- 处理结果应能进入风控规则和 AI 模型分析环节。
- 建议先使用本地可运行的示例事件和小规模数据完成端到端演示，再逐步扩展到真实流式处理。
- Kafka、Spark、Flink 的版本、运行方式、部署环境和最终选型待确认。

### 4.3 风控判断与评分

- 风险判断由风控规则和 AI 模型共同参与，输出风险评分。
- 风控结果至少应能关联到原始事件，并表达评分结果及判断依据。
- 评分范围、风险等级划分、规则配置方式、模型输入输出格式和规则与模型的组合方式待确认。
- 建议第一阶段使用可解释的示例规则和模拟模型结果，先打通数据流；后续再替换或接入真实模型。

### 4.4 数据存储

- 架构目标包含 Redis、MySQL 和 ClickHouse。
- MySQL 用于保存业务数据的建议方案；Redis 用于缓存的建议方案；ClickHouse 用于分析查询的建议方案。最终表结构、数据保留策略和组件分工待确认。
- 数据库连接配置不得在代码中硬编码密码或密钥；本地配置应通过环境变量等方式提供。

### 4.5 后端接口

- FastAPI 应提供管理平台和 AI Agent 所需的后端 API。
- 当前代码已提供根路径、演示问候接口、API 健康检查和数据库连通性检查。
- 后续建议逐步增加风险结果查询、风险详情查询和 Agent 分析接口；具体路径、请求响应格式和访问控制待接口设计阶段确认。
- API 应返回清晰、稳定的结构化数据；错误响应不应泄露数据库连接信息、密码或其他敏感内容。

### 4.6 风控管理平台

- Vue 3 前端目标是提供风控管理平台。
- 平台最终应能查看风险分析结果，并为用户理解和处理风险提供信息。
- 页面范围、筛选条件、图表、用户权限和操作流程待确认；建议先实现风险结果列表和单条详情，再增加统计分析页面。

### 4.7 AI Agent 分析与解释

- AI Agent 应能基于风险结果提供智能分析或解释。
- Agent 的输入数据范围、工具权限、输出结构、模型服务和错误处理策略待确认。
- 建议 Agent 先读取已有风控结果并生成解释，不直接修改风控记录或执行高影响操作；如需扩展操作能力，另行定义权限和确认流程。

## 5. 非功能需求

- **可学习：** 按初学者能理解的顺序拆分任务，解释重要概念和关键代码。
- **可运行：** 每个阶段都应有明确的本地启动和操作说明，尽量提供可复现的示例数据。
- **可维护：** 按职责组织代码，避免将数据库访问、业务判断和 API 路由长期堆在单个文件中。
- **安全：** 不提交密码、密钥、真实用户数据或本地环境文件；错误信息不得暴露敏感配置。
- **可追溯：** 代码变更按清晰实现点创建 Git commit；项目说明、架构、接口和运行方式变化时同步更新文档。
- **可解释：** 风险结果应逐步具备可读的判断原因，Agent 解释应能对应到系统已有的风险数据。

## 6. 分阶段实现建议

以下阶段是建议的实施顺序，方便在当前基础上循序渐进；不是架构图指定的唯一排期。

### 阶段一：Python API 与数据库基础

- 整理项目结构、依赖和本地运行说明。
- 通过环境变量管理数据库连接配置。
- 设计第一版风控事件和风险结果的数据模型。
- 实现数据库连通性检查及基础读写 API。
- 学习 Python 模块、函数、类型、FastAPI 路由、SQLAlchemy 和关系数据库基础。

### 阶段二：风控业务闭环

- 定义登录、下单、支付事件格式。
- 实现示例事件写入、基础规则判断和风险评分。
- 保存风险结果并通过 API 查询。
- 学习数据建模、输入校验、业务逻辑分层和错误处理。

### 阶段三：消息队列与实时处理

- 接入 Kafka，将事件生产和消费链路跑通。
- 选择 Spark 或 Flink 实现实时处理原型。
- 处理事件重复、异常数据和处理失败等情况。
- 学习消息队列、流处理、事件时间和数据管道。

### 阶段四：前端风控管理平台

- 使用 Vue 3 调用 FastAPI。
- 实现风险结果列表、详情和基础统计展示。
- 学习前后端接口协作、页面状态和数据可视化。

### 阶段五：AI 模型与 AI Agent

- 接入或构建风险模型，并明确模型输入、输出和评估方式。
- 让 AI Agent 基于风险事件、规则命中和模型结果生成分析解释。
- 为模型和 Agent 增加异常处理、日志和可追溯信息。
- 学习模型服务调用、提示设计、工具使用和 Agent 边界。

### 阶段六：多存储完善与项目交付

- 根据实际查询需求引入 Redis 和 ClickHouse，并验证各自的数据职责。
- 补充部署、配置、架构和操作文档。
- 整理可复现的演示流程和项目展示材料。

## 8. 待确认事项

随着项目推进，需要结合项目说明文档和学习进度逐步确定：

1. 项目的具体业务场景、用户角色和演示目标。
2. 用户行为事件及风险结果的字段定义。
3. Kafka、Spark 与 Flink 的最终选型和部署方式。
4. 风控规则、评分范围、风险等级和 AI 模型方案。
5. Redis、MySQL、ClickHouse 的数据职责、表结构和保留策略。
6. FastAPI 与 Vue 3 的接口清单、页面范围和权限要求。
7. AI Agent 使用的模型、工具、数据访问范围和输出格式。
8. GitHub 仓库地址、分支策略和本地开发环境要求。

在这些事项确认前，实现应采用简单、可替换的方案，并在代码或文档中清楚标明假设。

## 9. 验收目标

项目整体完成时，至少应满足以下目标：

- 能从示例行为事件开始，展示事件经过处理、风险判断、评分和存储的完整链路。
- 能通过 FastAPI 查询风险结果，并由 Vue 3 风控管理平台展示。
- 能通过 AI Agent 对已有风险结果生成可读且能追溯到输入信息的分析解释。
- 能按文档在开发环境启动和演示主要模块。
- 关键代码和架构能由项目维护者讲解清楚；项目文档与实际实现一致。
- 代码变更有清晰的 Git 历史，且仓库不包含密钥、密码或不应公开的数据。
